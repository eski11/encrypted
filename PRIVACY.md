# ENCPTD data handling

The current ENCPTD service is an independent custom server running on the owner's Windows PC. It does not use Matrix or Signal messaging services/accounts. Signal's libsignal library implements phone-to-phone encryption locally in the app.

The server stores usernames, salted scrypt password verifiers, hashed authentication tokens, public encryption-key bundles, routing metadata and queued ciphertext. It does not receive phone private keys or message text from the shipped client. Acknowledged messages are removed from the active queue; SQLite/WAL backups and storage media may retain historical ciphertext/metadata. Authentication/routing metadata remains visible to the server owner. Device and recipient compromise are outside message encryption's protection.

The owner console is separate from the phone API and binds only to this PC's loopback interface. Its private owner token is stored under `desktop/state/`; anyone with that token and local access can administer the service. Phone signup creates ordinary accounts without owner privileges. Protect the Windows login and that directory. No credential, token, real database or message history belongs in GitHub/Codemagic.

Automatic connection uses a public GitHub Gist containing a signed payload: server instance ID, current HTTPS address (or an offline marker), revision and validity times. GitHub retains file history, so previous connection addresses can remain public. The public key and Gist address are bundled in the app. The private Ed25519 signing key stays in `desktop/state/discovery.json`. The PC obtains GitHub credentials from Git's credential manager in memory when publishing; they are never bundled in the app or copied into the connection file. The app verifies signatures, instance, expiry and monotonic revisions before using a connection address. GitHub can observe discovery requests. This authenticates connection records; it does not hide server addresses or provide a security audit.

The optional Cloudflare Quick Tunnel exposes the phone API over a temporary HTTPS address. Cloudflare terminates the outer TLS connection. From version 0.3, the shipped phone app separately encrypts requests to a pinned PC transport key, including credentials, session tokens, inner API paths and routing fields. Responses use HPKE authenticated mode to prove possession of the PC key. Requests use fresh HPKE encapsulations and response keys, replay IDs and validity checks. Cleartext API fallback is rejected. Cloudflare still sees IP addresses, timing, the fixed transport endpoint, public health information and padded sizes. Earlier app versions sent credentials through Cloudflare's TLS termination; an update cannot retract previous exposure. Change your password in the updated app if it was used with that version. The test tunnel has no production uptime guarantee and still uses a third-party intermediary.

Phone keys, session records and local message history are saved in an AES-GCM encrypted vault. Version 0.3 migrates the same master key into a Keychain item requiring user presence and `WhenPasscodeSetThisDeviceOnly`, confirming the protected copy before removing the older copy. The key is not sent to the server. Locking releases app references to decrypted chat/key state; language/runtime memory and compromised-device limitations still apply. Detected recording/mirroring locks and covers the UI. Screenshot notification occurs after capture and cannot undo the image. Removing copy controls does not prevent recipients saving a copy by other means.

New message content includes an encrypted 24-hour expiry. Compliant apps prune expired local messages/outbox entries while open or on next unlock; older history without an expiry is preserved. A modified recipient can ignore expiry. The relay removes queued ciphertext after seven days and retry receipts after 30 days. New retry receipts omit explicit recipient IDs, but pending messages still need routing information and legacy receipts can remain until expiry. These operations are logical deletion, not guaranteed forensic erasure of flash storage, WAL files or existing backups.

The PC transport private key stays in `desktop/state/transport-key.json`, with its public key pinned in the app build. Compromise of the PC/key can expose credentials and routing data; the extra transport does not promise forward secrecy for recorded requests after transport-key compromise. Independent phone-to-phone message encryption remains a separate layer. Release obfuscation makes inspection harder but does not protect against a compromised endpoint or make the public source secret.

From version 0.4, saved phone accounts use separate encrypted vault files and master keys. The account index has an independent device-protected key. The original vault is copied and checked before its legacy key is retired; migration does not generate a replacement chat identity. When an app passcode is enabled, PBKDF2-HMAC-SHA256 with a random salt and 600,000 iterations derives a wrapping key for that account's master key. The six digits are not sent to the server. Counters, timers and wrapped keys live in device-protected Keychain records. These app-managed counters are not a hardware anti-rollback guarantee against a compromised OS, malicious app build or external snapshot restoration.

Optional automatic deletion is per account and disabled by default. The server stores the chosen rule, signed-unlock public key, last accepted event counter/time, short-lived challenges and hashes of narrowly scoped confirmation/deletion capabilities. Only a signed proof from the account's saved device resets its inactivity deadline. Retries of the same event do not extend it again. Preparing settings alone cannot activate server deletion; the phone first saves its new security record and then confirms. Enabling/changing rules requires the account password and proof of the saved account key when configured previously.

On a rule-triggered phone wipe, an authenticated tombstone is recorded before removing the account's key/file. An encrypted pending deletion job retains only that account's server UUID and deletion capability, until the PC acknowledges removal. The server removes that account's rows, sessions, device/public keys and queued messages involving it. It does not remove messages already copied to other phones or old backups. iOS cannot guarantee execution when the app is closed, so overdue phone vaults are checked before decryption on next use. A running PC checks the server deadline each minute; an offline PC enforces it on startup. Offline passcode entry cannot renew a server deadline until a valid proof arrives, and cannot resurrect an account already deleted. Accurate clocks and timely internet connectivity are required for this opt-in rule.

GitHub and Codemagic process the source/build configuration, and Apple/Sideloadly handle personal app signing separately. They do not need real chat accounts, passwords or encryption keys for this build. The custom app has no analytics or automatic crash-upload service. It still needs successful cloud tests, real-device testing and independent review before security claims beyond the implemented design are justified.

The 0.5 owner dashboard lists account usernames, device pairing, active login counts and queued-envelope counts without showing password verifiers or messages between other accounts. Optional PC chat is a separate conversation endpoint with its own Signal identity, explicit contact verification and a passphrase-encrypted local vault. Messages addressed to that PC can be read on the unlocked owner dashboard and in its process. The PC chat passphrase is also that PC account's login password; the server stores its password verifier. It is sent only to the localhost admin endpoint, not the public discovery file or a phone. Keep a strong unique passphrase. Signing out accounts revokes sessions but does not delete accounts or their phone keys.
